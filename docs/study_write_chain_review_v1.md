# 실험용 Write 프롬프트 체이닝 점검 v1

- 점검일: 2026-10-10. 샘플 사례 EQ008(고정 가상환자, 68세 여자 6회 방문)로 끝까지 돌린 결과를 보고 확인했다.
- 모델: 빠른 체인 `FAST_LLM_MODEL`(기본 gpt-4.1-mini), 품질 체인 `QUALITY_LLM_MODEL`(기본 gpt-4.1). `temperature 0`, JSON 객체 출력 강제, 스키마(zod) 검증 뒤 실패 시 재시도.
- 외부로 나가는 글은 모두 `assertOutboundTextIsSafe` 를 거친다. 이름·연락처 등 식별자가 남아 있으면 호출 자체가 막힌다. 실험용 Write 는 날짜만 가리지 않는다.

## 1. 전체 흐름

```
② 기록 넣기 (xlsx·docx → 방문별 텍스트)
③ 분석 (/process, 기존 Write 파이프라인)
   PREPROCESS 비식별(날짜 보존) → 전문용어 정규화(RAG) → 애매한 용어는 pendingTermConfirmations
   CHAIN1 기록 분할·근거 카드        (빠른 모델)
   CHAIN2 섹션별 작성 가능 여부      (빠른 모델)
   CHAIN3 섹션별 1차 초안            (품질 모델)  ← 기록으로 쓸 수 있는 섹션만
   CHAIN4 섹션별·공통 빠진 정보      (빠른 모델)
   CHAIN5 보완 질문 후보             (빠른 모델)
④ 질의응답
   1회차: 고정 질문 3개 (체인 없음)
   SW-Q2 2·3회차 질문 생성            (빠른 모델)
⑤ SW-D 답변 반영 섹션 초안 ×12       (품질 모델, 동시 3개)
   SW-C CARE 세부 항목 점검 ×12        (빠른 모델)
⑥ SW-R 섹션 채팅 수정                 (품질 모델) → 바뀌면 SW-C 다시
⑦ 직접 편집 (체인 없음)  ⑧ Word (체인 없음)
```

## 2. 체인별 입력·출력

| 체인 | 위치 | 입력 | 출력 | 모델 |
|---|---|---|---|---|
| SW-Q2 | `prompts/studyWrite_questions.ts`, `studyWrite/interview.ts` | 회차 번호·남은 질문 수, 지금까지의 질문과 답(비식별), **비식별 기록 전문**(16,000자까지), CHAIN3 초안 요약(섹션당 700자), CHAIN4 섹션별·공통 빠진 정보, CHAIN5 후보 질문 + CHAIN2의 recommendedQuestions, CARE 세부 항목표 | 질문 ≤3개: question, targetSectionIds, careItem, priority, rationale(참여자에게 숨김), stopReason | 빠름 |
| SW-D | `prompts/studyWrite_draft.ts`, `studyWrite/drafting.ts` | 섹션 id·이름, 그 섹션의 CARE 세부 항목, 비식별 기록 전문, CHAIN3 초안(없으면 "초안 없음"), 그 섹션에 쓰이는 질의응답 + 사례 전체 질문 | draftText, usedQuestionIds, notes | 품질 |
| SW-C | 같은 파일 | 섹션 id, CARE 세부 항목, 기록 전문, 질의응답, 현재 초안 | 항목마다 present / in_record_not_in_draft / not_in_record / not_applicable + hint | 빠름 |
| SW-R | 같은 파일 | 섹션 id, CARE 세부 항목, 기록 전문, 질의응답, 이전 지시 5개, 현재 초안, 이번 지시 | draftText, changeSummary, outOfRecordClaims | 품질 |

코드에서 덧씌우는 것:
- SW-Q2 의 targetSectionIds 는 번호("8")나 이름("진단 평가")로 와도 섹션 id로 정규화. priority 는 모델 값을 버리고 연구실 필수·선택 표(`careItems.ts`)로 정한다. 같은 careItem 은 한 회차에 하나만.
- SW-C 의 항목 목록은 코드의 표를 기준으로 맞추고, 모델이 빠뜨린 항목은 not_in_record 로 둔다.
- SW-R 이 초안을 바꾸지 않았으면 버전을 올리지 않고 채팅에만 남긴다.

## 3. 샘플에서 확인한 것

| 확인 | 결과 |
|---|---|
| CHAIN3 초안이 있는 섹션 | 8개 (환자 정보, 임상 소견, 타임라인, 진단 평가, 치료 개입, 추적 관찰, 환자 관점, 고찰은 비어 있음). 제목·초록·서론·동의는 CHAIN2가 IMPOSSIBLE 로 판정해 초안 없음 → SW-D가 기록과 답으로 새로 씀. 의도대로 |
| CHAIN4·CHAIN5 | 이 사례에서는 빠진 정보 0건, 후보 질문 0건. SW-Q2 는 CHAIN2 의 recommendedQuestions 7개와 기록 전문으로 질문을 만들었다 |
| SW-Q2 2회차 | 처음엔 기록에 있는 것(도네페질 시간 변경 이유)을 물었다 → 기록 전문을 넣고 "기록에 있으면 버린다"를 명시한 뒤, 3회차는 기록에 없는 것(감별 진단)을 물었다 |
| SW-Q2 중복 | 2회차에 8c 를 두 번 물었다(치매 진단 근거, 우울·화병 진단 근거) → 같은 careItem 하나만 남기도록 코드·프롬프트에 추가 |
| SW-D | 동의 섹션이 답대로("아직 받지 않았고 다음 내원 때") 쓰였다. 서론·고찰은 보고 이유·핵심 메시지로 틀을 잡고 "[문헌 보완 필요]"를 남겼다. usedQuestionIds 가 비어 왔다 → 프롬프트에 "한 문장이라도 썼으면 넣는다" 추가 |
| SW-C | 12섹션 점검. 선택 항목 빠짐만 보고됨(4b, 5d, 8b, 8d, 11a, 11b). 힌트 예: "기록 4회차에 K-MMSE 결과지가 있습니다" |
| SW-R | "약침 외 부작용은 없었다고 써 줘"에 "[기록 외 내용: 사용자 지시]"를 붙였다. 기록 6회차에 "그 외 특이 이상반응 없음"이 있어 붙이지 않는 것이 맞음 → "기록 전문에서 먼저 찾아본다"를 명시. 다시 확인 필요 |
| 전문용어 확인 | 이 사례는 애매한 용어 27건. 질의응답이 끝난 뒤 모달로 확인하거나 "확인 없이 초안 만들기"를 고를 수 있다. 27건을 다 보면 몇 분 걸리므로 세션에서는 건너뛰게 안내하는 쪽이 현실적 |

## 4. 아직 남은 약점

1. **기록 전문 16,000자 상한.** 긴 EMR(입원 기록 등)은 뒤가 잘린다. 잘리면 "…(이하 생략)"이 붙어 모델이 알 수는 있지만, 뒷부분 빈칸을 묻지 못한다. 전문가 기록 길이를 보고 상한을 올리거나 섹션별로 관련 방문만 넣는 방식으로 바꿀 수 있다.
2. **SW-D 는 근거 카드(CHAIN1)를 쓰지 않는다.** 기록 전문을 통째로 보므로 근거 카드가 없어도 되지만, 기존 Write 의 문장 단위 근거 연결(traceability)은 실험용 Write 초안에는 없다. 연구용으로 "어느 문장이 어느 방문에서 왔는지"가 필요하면 추가해야 한다.
3. **SW-C 판정은 모델 판단이다.** "기록에 있음"이 틀릴 수 있다. 참여자에게는 "확인이 필요합니다"로만 보이고 채점에 쓰지 않는다.
4. **"기록 외 내용" 표시의 민감도**는 전문가 사례로 다시 봐야 한다 (3절).
5. **고정 사례는 비식별을 건너뛴다.** 실제 기록에서의 비식별 결과(이름이 가려지고 날짜는 남는지), 전문용어 확인 흐름은 실제 기록으로 한 번 더 돌려 봐야 한다.
6. **CHAIN4·CHAIN5 가 비어 있을 때** SW-Q2 는 CHAIN2 추천 질문과 기록 전문에 의존한다. 이 경우 질문의 질이 기록 전문 읽기에 달려 있다.

## 5. 프롬프트 버전

| 체인 | 버전 | 바뀐 점 |
|---|---|---|
| SW-Q2 | v1 (2026-10-10) | 기록 전문 입력, 섹션 id 표기, 같은 careItem 중복 금지 |
| SW-D | v1 | usedQuestionIds 규칙 명시 |
| SW-C | v1 | — |
| SW-R | v1 | 기록에 있는 내용은 표시하지 않음 |

프롬프트를 바꾸면 이 표와 코드의 `*_PROMPT_VERSION` 을 같이 올린다. 저장된 초안·질문에는 생성 당시 버전이 남는다.
