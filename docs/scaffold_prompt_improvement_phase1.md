# Scaffold 프롬프트 개선 — 분석, 평가, 적용 (2026-10-12)

1단계(§1~§7)에서는 서비스 프롬프트와 고정 연구 자료를 바꾸지 않고 개선 후보를 만들어 평가했다. 2단계(§8)에서 후보 v3.2를 서비스에 적용하고 다른 기록 두 개로 평가했다. 3단계(§9)에서 섹션별 생성을 평가했다. 4단계(§10)에서 공개 단계를 공개 섹션 전용 생성으로 바꾸고 v3.3 규칙을 서비스에 넣었다(v4). 5단계(§11)에서 생성 뒤 코드 거르기를 붙였다. 고정 연구 자료(학생 V1, Scaffold V2)는 여전히 그대로다.

## 1. 요약

- **평가한 것:** Scaffold 화면이 실제로 보여 주는 LLM 출력은 CHAIN3 섹션 초안과 CHAIN1 근거 카드다. 그래서 CHAIN3부터 평가했다.
- **평가 기준:** 고정 연구 사례의 치료 개입 초안을 연구자가 만든 CARE 정리표의 22개 항목에 비추어 채점했다. 9a 치료 종류, 9b 시행 방법, 9c 변경과 이유다.
- **결과:**
  - 지금 Scaffold 프롬프트(v2)는 22개 중 13개를 담고, 기록과 다른 문장은 없었다.
  - 개선 후보 v3.2는 18~20개를 담았다. 3회 중 1회에서 날짜 하나를 옮겨 쓴 오류가 나왔다.
  - 참가자가 실제로 본 고정 초안(10-04 프롬프트)은 11개였고, 오류는 2건이었다.
- **늘어난 부분:** 시행 방법(한약 용량·용법·기간, 침 규격, 약침 부위별 용량)과 치료 변경(약침 부위 추가, 약침 중단, 태양혈 추가, 도네페질 복용 시간)이다.
- **한계:** 사례 하나, 조건마다 1~2회로 평가했다. 적용 전에 다른 사례로 확인해야 한다(§6, §7).
- **함께 고친 버그:** CHAIN3·CHAIN7의 출력 토큰 상한이 실제 출력보다 작아, 보통 크기의 사례에서 초안 생성이 실패할 상태였다. 32,000으로 올렸다(커밋 `9d058a3`). 상한을 적용한 뒤 실제로 실패한 처리는 없었다.

## 2. Scaffold가 쓰는 LLM 출력

| 체인 | Scaffold에서 쓰는 곳 | 고정 연구 사례(학생 V1, V2) |
|---|---|---|
| CHAIN1 근거 카드 | 기록 보기, 근거 연결 선택 | 저장된 결과를 쓴다(LLM 호출 없음) |
| CHAIN2 섹션 판정 | 섹션 상태 설명 한 줄 | 저장된 결과 |
| CHAIN3 섹션 초안 | 공개 뒤 AI 초안, Step 3 문장 판단의 대상 | 저장된 결과(2026-10-04 생성). 프롬프트를 고쳐도 다시 얼리지 않으면 바뀌지 않는다 |
| CHAIN4/5 누락·질문 | 화면 후보 목록 코드가 주석 처리되어 지금은 쓰지 않음 | 저장된 결과 |
| 적정성 검토 | 실험용 Scaffold는 생성하지 않음(F단계 수정) | – |
| 용어 판정기 | 전처리(확인 요청) | 저장된 결과 |

일반 Scaffold 사례(고정 사례가 아닌 것)는 지금 DB에 실험용만 있어, 실제로 새로 처리되는 Scaffold 사례는 아직 없다. 개선 효과는 앞으로 일반 Scaffold로 쓰는 사례나, 새 연구를 위해 고정 자료를 다시 만들 때 나타난다.

## 3. 평가 방법

- **입력:** 고정 연구 사례의 근거 카드 230개와 섹션 상태(`defaultStudyCaseProcessed.generated.ts`)를 그대로 쓴다. 고정 파일은 읽기만 한다.
- **모델:** gpt-4.1, temperature 0. 서비스와 같은 호출 경로를 쓴다(`callLLMWithSchema`, 체인별 상한).
- **채점 기준:** `DEFAULT_STUDY_CARE_ELEMENT_MAP.THERAPEUTIC_INTERVENTIONS`의 "기록에 있는 정보"를 22개 확인 항목으로 나눴다(`backend/scripts/promptEval/scaffoldTiChecklist.ts`). 정규식으로 1차 채점하고, 초안을 사람이 원문과 대조해 읽었다.
- **오류 판정:** 사람이 대조해 찾은 오류는 판정 규칙으로 추가했다. 자동 판정이 틀린 두 건은 문장·괄호 단위로 고쳤다. 아래 표의 오류 수는 최종 규칙과 사람 판독이 일치하는 값이다.
- **재현:**
  ```bash
  npm run eval:scaffold-prompt -- --variant current --dates
  ```
  `--variant`는 `frozen`, `current`, `candidate` 중 하나다. `--dates`는 근거 줄에 방문 날짜를 붙이고, `--runs 2`는 반복 횟수다. 결과는 `backend/data/prompt-eval/`(git 밖)에 저장된다.
- **비용:** 이번 평가 전체가 14회 호출, 1.75 USD(약 2,450원)였다. 토큰 상한 때문에 잘린 4회를 포함한다. 사용량 기록에는 caseId `eval:scaffold-chain3`으로 남는다.

## 5. 후보 v3.2가 바꾼 것

2단계에서 서비스 프롬프트 `backend/src/llm/prompts/scaffold/chain3_draft.ts`(SCAFFOLD-CHAIN3 v3)로 옮겼다. 후보 파일은 지웠고 이력은 git에 있다. 이 사례에만 맞춘 약 이름이나 혈위 이름은 넣지 않았다.

1. **역할:** 이 초안은 학습자가 자기 초안과 비교하고, 문장마다 기록과 대조하는 자료라는 점을 밝힌다.
2. **검증 가능한 문장:** 한 문장에는 같은 근거로 확인되는 사실만 담고, 다른 방문이나 다른 치료의 사실을 뭉치지 않는다.
3. **날짜·기간·보고 시점:** 기록된 날짜를 그대로 쓰고, 기간의 시작점을 옮기지 않는다. "~했다고 함"은 보고된 방문으로 쓴다.
4. **이유·목적·계획:** 기록에 적힌 경우에만 쓴다.
5. **행위 주체:** 환자가 한 일과 의료진이 지도한 일을 바꾸지 않는다. 보호자 전달은 보호자 진술로 쓴다.
6. **자료 설명 금지:** 본문에 "기록" 같은 자료 설명을 넣지 않는다.
7. **치료 개입 지침:**
   - 이 기관의 치료와 다른 기관의 약을 구분한다.
   - 재현에 필요한 세부를 생략하지 않는다(한약·침·약침·그 밖의 요법별 항목).
   - 반복 처치는 한 번만 쓰고 시행 범위를 밝힌다.
   - 변경마다 무엇을·언제·기록된 이유를 쓴다.
   - 이상반응과 경과는 추적 결과 섹션으로 보낸다.
8. **추적 결과:** 기록된 이상반응은 이 섹션에 쓴다.

입력 쪽 후보로 근거 줄에 방문 날짜를 붙이는 방법(`--dates`)도 평가했다. 한약 기간처럼 날짜가 필요한 항목이 더 잘 나온다. 다만 v3.2에서는 날짜 없이도 19개를 담았고, 남은 날짜 오류 1건은 날짜가 있는 조건에서 나왔다. 날짜 입력은 공유 코드의 선택 인자이며 지금은 꺼져 있다(`buildChain3Inputs(..., { includeVisitDates })`).

## 6. 한계

- **사례:** 고정 연구 사례 하나다. 채점표도 이 사례 기준이라, 후보가 이 사례에 맞춰졌을 위험이 있다. 규칙은 일반 표현으로만 썼지만 다른 사례로 확인하기 전에는 일반화할 수 없다.
- **반복 횟수:** 조건마다 1~2회다. temperature 0이어도 결과가 달라진다(v3.2 날짜 있음 1회차 18개, 2회차 20개).
- **채점 범위:** 치료 개입만 채점했다. 다른 6개 섹션은 사람이 일부만 읽었다. 추적 결과 섹션에서 기록된 이상반응과 "그 외 특이 이상반응 없음"을 바르게 쓴 것은 확인했다. 그 밖의 섹션은 체계적으로 보지 않았다.
- **길이:** 후보 초안은 고정 초안보다 길다(약 870~1,070자, 고정 초안 504자). Step 3에서 학습자가 판단할 문장 수가 늘어난다. 교육 설계상 괜찮은지는 연구자 판단이 필요하다.
- **CHAIN1:** 근거 카드 쪽은 이번에 평가하지 않았다.

## 7. 정할 것

1. **적용 범위.** 권고는 v3.2를 Scaffold 서비스 프롬프트로 올리는 것이다. 이때 버전은 `SCAFFOLD_CHAIN3` v3, 공개 단계 `CHAIN3_STUDY_REVEAL` v3가 된다.
   - 영향은 앞으로의 일반 Scaffold 사례와, 고정 결과가 없을 때의 공개 단계뿐이다.
   - 학생 V1과 Scaffold V2의 고정 초안은 그대로다.
   - 고정 초안을 새 프롬프트로 다시 얼리는 것은 별도 결정이다. 다시 얼리면 V1과 V2 참가자가 서로 다른 AI 초안을 보게 되어 비교가 깨진다. V2 교수 평가 전에는 하지 않기를 권한다.
2. **추가 사례 평가.** 적용 전에 다른 기록 1~2개로 사람이 읽어 확인할지 정한다. 실험용 Write 전문가 기록 프리셋이 후보다. 정답표가 없어 사람 판독이 필요하고, 1회당 약 0.2 USD다.
3. **방문 날짜 입력.** Scaffold 세트에서 켤지 정한다. 권고는 추가 사례 평가 뒤 결정이다.
4. **초안 길이.** Step 3 판단 부담을 고려해 상한(예: 섹션당 문장 수)을 둘지 정한다.
5. **다음 대상.** 다른 섹션(특히 추적 결과)과 CHAIN1 근거 카드를 이어서 평가할지 정한다.

## 8. 2단계: 서비스 적용과 다른 기록 평가

### 8-1. 적용한 것

- **서비스 프롬프트:** Scaffold CHAIN3 서비스 프롬프트를 v3.2 본문으로 바꿨다(`prompts/scaffold/chain3_draft.ts`).
- **버전:** 레지스트리를 `SCAFFOLD-CHAIN3:v3`, `CHAIN3_STUDY_REVEAL:v3`으로 올렸다. 공개 단계 템플릿 해시는 `00406d6d…`이고, 테스트(`tests/llm/promptSets.test.ts`)가 이 값을 고정한다.
- **이전 v2 본문:** 비교 평가용으로 `backend/scripts/promptEval/baselines/scaffoldChain3V2.ts`에 남겼다.
- **방문 날짜 입력:** 근거 줄에 방문 날짜를 붙이는 입력은 켜지 않았다. 서비스 입력은 지금까지와 같다(§8-3).
- **고정 연구 자료가 그대로인 이유:** 공개 단계(`routes/scaffold.ts`)는 고정 초안이 있는 사례에 버전과 관계없이 고정 초안을 먼저 돌려준다. 학생 V1, V2 참가자, V2 테스트 사례는 모두 같은 고정 사례다. 학생 V1과 Scaffold V2 테스트가 통과했다.
- **영향 범위:** 앞으로 처리되는 일반 Scaffold 사례다. 캐시 지문이 바뀌어 기존 일반 Scaffold 사례는 다음 처리 때 CHAIN3가 한 번 다시 돈다.

### 8-2. 다른 기록 평가

평가 도구에 `--source`를 더했다.
- `case:<사례 id>`: DB의 처리된 사례를 읽기만 해서 그 근거 카드와 섹션 상태를 쓴다.
- `sample:hwa-byung`: 저장소의 샘플 입력을 처음 한 번 전처리·CHAIN1·CHAIN2로 처리해 저장하고, 두 프롬프트에 똑같이 넣는다.

정답표가 없으므로 판단은 초안을 근거와 대조해 읽어서 했다. 사례와 무관한 보조 지표도 함께 냈다. 근거의 용량·횟수·시간 같은 숫자+단위 표기가 초안에 남은 비율과, 근거에 없는 숫자+단위 표기(날짜 제외)다.

## 9. 3단계: 섹션별 생성 평가

### 9-1. 준비 (서비스 동작은 그대로)

- **프롬프트 생성 함수:** Scaffold CHAIN3 프롬프트를 섹션 목록을 받아 만드는 함수로 바꿨다(`buildScaffoldChain3SystemPrompt(sectionIds)`). 기본값(7개 섹션)은 v3 본문과 글자까지 같다. 공개 단계 해시 `00406d6d…`가 그대로임을 테스트로 확인했다. 섹션을 지정하면 그 섹션의 작성 범위·지침·출력 형식만 남긴다.

1. **섹션별 생성은 효과가 크다.** 긴 기록에서 치료 개입의 구체성이 2~3배가 되고, 고정 사례 점수도 가장 높다. 비용은 1/2~1/3, 시간은 약 1/3이다. 다만 위 문제 1~4가 새로 생기거나 늘어나므로, 그대로 켜기 전에 규칙을 한 번 더 손봐야 한다.
2. **근거 범위는 한쪽이 확실히 낫지 않다.** 전체 근거가 고정 사례에서는 더 정확했다(안와부·태양 경위). 교수 기록에서는 지어낸 문장이 섞였다. 권고는 치료 개입 근거에 타임라인 근거만 더하는 중간 범위를 시험하는 것이다.
3. **정할 것:**
   - **(가) 적용 범위:** 공개 단계의 실시간 생성 경로를 치료 개입 전용 프롬프트로 바꿀지 정한다. 지금 이 경로는 7개 섹션을 요구하면서 치료 개입 근거만 넣는다. 고정 초안이 있는 연구 사례에는 영향이 없다.

   - **(다) 단위:** 단위가 적히지 않은 약재 양에 g을 붙여도 되는지 정한다. 붙이지 않는다면 규칙을 더 강하게(예시 포함) 써야 한다.
   - **(라) v3.3 규칙:** 다음 반복에서 서비스에 넣을지 정한다. 없는 내용 서술은 막았고, 단위와 자료 설명 문장은 아직 못 막았다.
4. **비용:** 3단계 평가는 23회, 1.09 USD였다. 1~3단계 합계는 3.77 USD다.

## 10. 4단계: 공개 단계 섹션 전용 생성과 v4 적용 (2026-10-12)

### 10-1. 바꾼 것

1. **Scaffold CHAIN3 v4:** 작업 규칙 11~13을 더했다. 11은 없는 내용 서술 금지, 12는 표기 보존, 13은 마무리 문장 금지다. 7개 섹션 생성과 섹션별 생성에 모두 적용된다. 버전은 `SCAFFOLD-CHAIN3:v4`, `CHAIN3_STUDY_REVEAL:v4`다. 이전 v3 본문은 `backend/scripts/promptEval/baselines/scaffoldChain3V3.ts`에 남겼다.
2. **공개 단계 실시간 생성:** 공개하는 섹션 하나만 생성한다(`routes/scaffold.ts`).
   - 근거는 지금처럼 그 섹션 근거만 넣는다.
   - 생성 메타데이터의 `promptTemplateHash`는 그 섹션에 실제로 보낸 프롬프트로 계산한다(`templateHashOf`). 계산 방식은 레지스트리와 같다.
   - CHAIN3의 7개 섹션이 아닌 섹션은 이전처럼 전체 프롬프트를 쓴다.
3. **CHAIN3 실행 함수:** `runInitialSectionDrafts`가 `sectionIds`를 받는다. Scaffold 세트에서만 허용하고, 요청하지 않은 섹션의 결과는 버린다.
4. **레지스트리:** 공개 단계 대표 프롬프트를 치료 개입 전용 프롬프트로 등록했다. 해시는 `c9c8ca48…`이고 테스트가 고정한다.

**영향 범위:**
- **고정 초안이 있는 사례:** 공개 단계는 고정 초안을 먼저 돌려준다. 학생 V1, V2 참가자, V2 테스트 사례는 모두 여기에 해당하므로 초안이 바뀌지 않는다.
- **일반 Scaffold 사례:** 처리(7개 섹션 생성)에 v4 규칙이 적용된다. 캐시 지문이 바뀌어 다음 처리 때 CHAIN3가 한 번 다시 돈다.

**자동 테스트:** 백엔드 테스트 33개가 통과했다.

- 섹션별 실행이 프롬프트·입력을 그 섹션으로 줄이고 다른 섹션 결과를 버리는지
- Write 세트에서 섹션 지정이 거부되는지
- 공개 단계 해시

**서비스 경로 생성:** 평가 도구가 서비스 함수(`runInitialSectionDrafts` + `sectionIds`)를 그대로 불렀다. 치료 개입 근거만 넣었고, 공개 단계와 같은 조건이다.

| 기록 | 회 | 정리표 /22 | 기록과 다른 문장 (사람 판독) | 길이 | 없는 내용 서술 | 단위 붙이기 |
|---|---:|---:|---|---|---:|---|
| 고정 사례 | 2 | 20, 20 | 1회에 "1일 3회"를 "1회 3회"로 쓴 오기 1건 | 1,527 / 1,908자 | 0 | 없음 |
| 교수 내과 기록 | 2 | – | 1회차: "구체적 혈위는 기록되어 있지 않다"(사실과 다름) | 976 / 830자 | 1, 0 | 1회차 g 8개 |
| 샘플 화병 | 1 | – | 없음 | 154자 | 0 | 없음 |

- **자동 오류 판정 정정:** 고정 사례 1회차에서 "도네페질 변경 안내" 오류로 잡힌 문장은 실제로는 기록과 맞았다("신경과 문의, 딸 전달"). 이상반응으로 잡힌 문장도 "멍이 들 수 있음을 설명"이라는 사전 설명이었다. 둘 다 오판이다.
- **고정 사례:** 지금까지 가장 좋은 결과다. 시행 회차 범위, 회차별 상담 시간과 내용, 약침 용량 조정, 혈위 추가 경위가 모두 들어갔다.
- **교수 내과 기록:** 실행마다 품질이 크게 달랐다.
  - 1회차는 규칙 11(없는 내용 서술)과 12(단위)를 어겼고, "기록되어 있다"류 자료 설명 문장도 썼다.
  - 2회차는 단위를 지켰지만 처방 시점을 다시 뭉쳐 썼다.

### 10-3. 남은 과제

1. **긴 기록에서 규칙 11·12가 지켜지지 않는 경우:** 같은 입력에서도 실행마다 다르다. 생성 뒤 코드로 거르는 방안을 고려할 만하다. 예를 들어 "기록되어 있지 않다" 문장을 빼고, 근거에 없는 숫자+단위 표기를 표시한다.
2. **"1일 3회"를 "1회 3회"로 쓰는 오기:** 근거의 "1C tid"에서 생기는 것으로 보인다. 여러 번 나왔다.
3. **일반 Scaffold의 섹션별 생성(정할 것 나):** 아직 바꾸지 않았다. 다른 섹션은 평가하지 않았다.
4. **단위 g(정할 것 다):** 결정되지 않았다. 지금 규칙은 붙이지 않는 것이다.
5. **비용:** 4단계 확인은 5회, 0.19 USD였다. Scaffold 프롬프트 평가 전체 합계는 3.96 USD다.

## 11. 5단계: 생성 뒤 코드로 거르기 (2026-10-12, SCAFFOLD-FILTER:v1)

긴 기록에서는 v4 규칙 11·12가 실행마다 들쭉날쭉했다(§10). 그래서 Scaffold CHAIN3 출력을 코드로 한 번 더 거른다. 파일은 `backend/src/llm/postFilters/scaffoldDraftFilter.ts`다.

**적용 범위:**
- Scaffold 세트의 CHAIN3에만 적용한다. 일반 Scaffold 처리(7개 섹션)와 공개 단계 실시간 생성이 여기에 해당한다(`runInitialSectionDrafts`). Write 세트에는 적용하지 않는다.
- 고정 초안(학생 V1, V2)은 생성하지 않으므로 거르지 않는다.
- 근거 연결(휴리스틱)은 거른 본문으로 계산한다.

**원칙은 "확실한 것만 고치고, 애매한 것은 표시만"이다.**

| 대상 | 처리 |
|---|---|
| 무엇이 기록에 없는지만 말하는 문장 | 뺀다. 대상은 "~은 기록되어 있지 않다", "기재·명시되어 있지 않다", "기록에 나타나지 않는다", 그리고 정보·언급·기록과 함께 쓴 "확인되지 않는다"다 |
| 사실 절 뒤에 붙은 없는 내용 | 사실 절만 남긴다("~하였으며, … 기록되어 있지 않다" → "~하였다.") |
| "~된/한 기록이 있다", "기록된 바와 같이" | "~되었다/하였다"로 바꾸고, "기록된 바와 같이"는 지운다 |
| 근거에 단위 없이 적힌 약재 양에 붙인 g | 근거에 "약재 9"처럼 있고 "9g"이 없을 때만 뗀다 |
| 용법 오기 "1회 3회" | "1일 3회"로 고친다 |
| 마지막 문장이 "이상의/이러한 … 치료 … 반복·지속·조정·병행·적용되었다" | 뺀다 |
| 근거에 없는 숫자+단위 표기, 사실과 섞인 "기록되어 있다" 문장 | 고치지 않고 표시만 한다 |

"특이 소견은 확인되지 않았다"처럼 기록된 음성 소견과, "처방 사유는 … 기록되어 있다"처럼 문서 내용을 옮긴 문장은 건드리지 않는다. 고치거나 표시한 내용은 초안의 `postFilter`에 남는다. 고친 것이 없으면 이 필드도 없다.

**확인:**
- **단위 테스트:** `npm run test:scaffold-filter`. 예문은 평가에서 실제로 나온 문장이다.
- **저장된 결과에 소급 적용:** 평가 결과 182개 섹션 초안(모든 판, 모든 섹션)에 거르기를 돌려 봤다. LLM 호출은 없었다.

| 항목 | 건수 |
|---|---:|
| 바뀐 초안 | 20 / 182 |
| 뺀 문장 | 15 |
| 사실 절만 남긴 문장 | 8 |
| "~된 기록이 있다" 등 바꿈 | 12 |
| 뗀 단위 g | 115 |
| 오기 수정 | 5 |
| 표시만 한 수치 | 19 |
| 표시만 한 자료 설명 문장 | 69 |

바뀐 내용을 모두 사람이 읽었다.
- **뺀 문장과 잘라 낸 절:** 모두 없는 내용 서술이나 마무리 요약이었다. 사실이 사라진 경우는 없었다.
- **뗀 단위:** 모두 근거에 단위 없이 적힌 약재 양이었다.
- **아쉬운 경우 1건:** "치료의 구체적 시기와 내용은 내원별로 반복적으로 기록되어 있으나, … 추가 정보는 확인되지 않았다"는 앞 절만 남아 자료 설명 문장이 됐다. 이 문장은 표시만 된다.

**남은 것:**
- 사실과 섞인 자료 설명 문장("구성 약재와 용량은 … 구체적으로 기재되어 있으며, 예를 들어 …")은 표시만 하고 고치지 않는다. 고치려면 문장을 다시 써야 해서 코드로 하기에 위험하다.
- 거르기 규칙을 바꾸면 `SCAFFOLD_DRAFT_FILTER_VERSION`을 올린다.
